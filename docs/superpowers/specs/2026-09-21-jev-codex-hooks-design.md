# Jev による Codex の軌道修正

状態: ユーザー承認済み、実装と単体・実 API 検証済み。Codex での新しい Hook の信頼登録と、実セッションでの自動発火確認は未実施。

## 目的

Codex 全体を対象に、過剰な検証、目的からの逸脱、進展に見合わない極端なトークン消費の反復を Jev に判断させる。固定の行動パターンや回数だけで判定せず、現在の目的、指示、作業状況の関係を評価する。

大量のトークンを消費していても、依頼の達成に必要で着実に進んでいる作業には、それだけを理由に介入しない。ユーザーの明示指示と適用される必須チェックを判断材料に含める。

## 判定と介入

1. グローバルな `PostToolUse` Hook をツール実行後ごとに起動する。
2. そのセッションの観測情報から state を構成し、Jev に評価させる。
3. Jev の判定値に基づき、必要な場合だけ Hook が定型の再考指示を組み立てる。
4. `hookSpecificOutput.additionalContext` で Codex に指示を渡す。
5. Codex が具体的な修正方針を考えて作業を継続する。

強制停止、ツール結果の置き換え、ユーザーへの判断の丸投げは行わない。実行中の長い処理や Hook 間の消費には途中介入できない。

## State

TypeSafe の state は判定対象と根拠をまとめたデータであり、判定の質問とは分ける。名前付きの JSON フィールドで、次の情報を関連づける。

- ユーザーの依頼と追加指示
- 適用される作業ルールと必須チェック
- 観測できる計画と進捗
- 直近のツール呼び出しと結果、変更差分
- 取得できるトークン使用量とその推移
- 過去の介入内容と、その後の行動

会話とコードの必要部分を TypeSafe API に送る方針はユーザーと合意済み。取得できない情報は不明とし、非公開の内部思考の取得は前提にしない。実測使用量と出力量などの代替指標を混同しない。

## 判定の責務

Jev が文脈から再考の必要性を判定する。Hook は状態の収集、API 呼び出し、判定値の取り扱い、指示文の組み立てを担当する。具体的な作業方針の再考は Codex が担当する。

目的との整合性と、成果に対するトークン消費の妥当性を評価対象とする。具体的な迷走パターンの列挙を検出範囲の上限にしない。

指示文の例: 「現在の目的・直近の成果・トークン消費を照合し、同じ行動を続ける必要性を再検討してください。」

## 継続と失敗時の動作

介入履歴と介入後の行動を次の state に含め、改善していれば指摘を止める。問題が続けば再考を促すが、同じ指摘の連発を抑える。

材料不足、通信失敗などで判定できない場合は記録し、Codex の作業を継続する。

## 実装

`config/codex/hooks/jev-monitor.py` をグローバルな `hooks.json` に登録する。既存の Home Manager のディレクトリ参照で配布するため、Nix の宣言追加や switch は不要。

- Fish から起動し、既存の環境変数読み込み経由で `TYPESAFE_API_KEY` を受け取る。キーをスクリプトに埋め込まない。
- Python 標準ライブラリで TypeSafe API を呼ぶ。モデルは実測した `jev-1.13.0` に固定。
- 目的との整合性とトークン浪費の2つの Noul を同じ state で評価する。いずれかが 0.85 以上なら再考指示の候補とする。この値は少数ケースでの初期値であり、精度保証ではない。
- 同じ観点の通知は、成功した判定3回につき最大1回。同時実行ではセッションと transcript ごとのロックを使い、重複する判定は記録してスキップする。
- API のタイムアウトは8秒、Hook 全体は12秒。同期実行し、次のモデル処理へ指示を渡す。
- JSONL を前回の読取位置から読み、遅れが大きい場合は先頭側と最新側を各512 KBまで読む。最初のユーザーメッセージ4件、最新5件、直近のツールと公開発言、観測したルールを抜粋して保持する。
- state は24,000 UTF-8バイト以下。省略や取得不能を明示する。計画・差分・ルールは記録に現れた範囲のみ扱い、リポジトリ全体を毎回走査しない。
- `token_usage_record` の使用量を優先し、旧形式の `token_count` も扱う。内部思考の記録は除外する。
- セッション状態と最新判定は `~/.local/state/codex-jev-monitor/` に保存する。ディレクトリは0700、ファイルは0600で作成する。会話・ツール出力の抜粋を含むため Git 管理しない。保存期間による自動削除は未実装。
- `JEV_MONITOR_STATE_DIR` で検証用の保存先を指定できる。`--dry-run` は API 呼び出しと状態保存をせず、送信予定の JSON を表示する。

既知の API キーは送信データと保存データから除くが、任意の秘密情報を完全に検出する機能ではない。

## 運用上の確認事項

- Codex の `/hooks` で新しい `PostToolUse` の定義を信頼する。新規・変更された Hook は信頼登録までスキップされる。
- 初回のツール実行後、状態ファイルの `last_result` と必要時の再考指示を確認する。無効化も `/hooks` から行う。
- Hosted WebSearch など、Codex が Hook を発火しないツールはその場では監視できない。後続の対応ツールの実行時に記録から観測できる範囲で評価する。
- transcript は安定した公開インターフェースではない。Codex 更新後に取得可否を確認する。

既存の未コミット変更は保持する。Hook の信頼状態は手動で書き換えない。

## 検証範囲

必要な検証を継続するケース、成果の乏しい高コスト反復を再考するケース、介入後に改善するケース、判定失敗でも作業が継続するケースを確認する。Hook の実際の発火と再考指示の受け渡しを確認し、設定配布を変更した場合はリポジトリ指定のチェックを実行する。
