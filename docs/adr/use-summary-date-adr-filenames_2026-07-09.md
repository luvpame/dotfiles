# Use summary-date ADR filenames

Date: 2026-07-09

## Status

Accepted

## Context

このリポジトリには、設計判断を残すための ADR スキルがある。
ADR の保存場所とファイル名が決まっていないと、将来のエージェントや開発者が同じ判断を別々の場所に残しやすい。

ADR の命名には、連番、日付プレフィックス、内容要約と日付の組み合わせがある。
このリポジトリでは、人間とエージェントの両方がファイル名から内容を探せることを優先する。

## Decision

ADR は `docs/adr/{summary}_{yyyy-mm-dd}.md` に保存する。
`summary` は短い英語の kebab-case にする。
日付は ADR を作成する時点のローカル日付を使う。

連番は使わない。
日付だけで内容を表すファイル名も使わない。

## Options Considered

- **連番を使う**：作成順は分かりやすいが、内容を知るにはファイルを開く必要がある。番号の採番もエージェントが衝突を避けるために既存 ADR を毎回確認する必要がある。
- **日付を先頭に置く**：時系列で並べやすいが、同じ日に複数 ADR を作る場合は内容の識別が後ろに流れる。
- **内容要約と日付を組み合わせる**：ファイル名から内容を推測でき、同日の複数 ADR も区別しやすい。要約の付け方には裁量が残るが、短い kebab-case に限定すれば検索しやすい。

## Consequences

ADR の一覧を見たときに、内容と作成日を同時に把握しやすくなる。
エージェントが新しい ADR を作るときも、保存先と命名規則を迷わず適用できる。

一方で、同じ決定に近い summary を付けるとファイル名が似る。
作成前に `docs/adr/` を確認し、同名ファイルがある場合は上書きせず summary を変える。
