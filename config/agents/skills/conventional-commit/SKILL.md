# Conventional Commits

メッセージだけの依頼は、案を提示して完了する。ステージングと `git commit` は、コミット実行を依頼された場合に行う。
スキル名や type、subject のヒントだけでは、実行の許可とみなさない。
実行を依頼済みなら、対象選定から結果確認まで進め、同じ許可を取り直さない。

## メッセージ

- 基本形式は `type(scope): subject`。scope はプロジェクトの規約を優先し、規約がなければ共通モジュールを自然に特定できる場合に付ける。
- type は差分から選ぶ。挙動の修正は `fix`、機能追加は `feat`、挙動を変えない整理は `refactor`、文書は `docs`、その他は適切な標準 type を使う。
- subject は何をどう変えるかを簡潔に書き、絵文字と末尾の句読点は付けない。目安は64文字以内。既定言語は日本語で、ユーザーやプロジェクトの指定を優先する。
- body は理由や背景が必要な場合だけ付ける。1行72文字以内を目安にする。
- 引数は type や subject のヒントとして扱う。

## 対象と分割

`git status --short`、`git diff --staged`、`git diff` で現在の変更を確認する。
未追跡ファイルを含める場合は、その内容も読む。
依頼と無関係な変更は含めず、コミット対象の内容を書き換えない。
既にステージされた無関係な変更がある場合は、その状態を保ち、対象だけをコミットできる方法を選ぶ。

変更が1つの論理単位なら1コミットにする。
独立した責務が混在し、分けても各コミットが成立するなら、対象ファイルとメッセージを整理して分割する。
対象や分割方針を依頼から決められず、履歴や他の変更へ影響する場合だけ、推奨案を添えて確認する。

## 実行

リポジトリの必須チェックを確認し、未実施なら実行する。既に通過し、その後に関連変更がなければ繰り返さない。

1. 対象差分とメッセージを確定する。
2. 対象だけをステージし、コミット直前の差分に無関係な変更がないことを確認する。同じファイルに別の変更がある場合も対象を分ける。
3. `git commit` を実行する。body がある場合はメッセージを一時ファイルに保存し、`git commit --file <path>` で渡す。
4. 分割する場合は、コミットごとに2と3を繰り返す。
5. コミットされた差分と `git status --short` を確認し、コミットID、メッセージ、残った変更を報告する。

失敗した場合は原因を確認し、結果が不明なまま再実行しない。既にコミットが作られていないか確認する。
push や履歴の書き換えは、このスキルの実行に含めない。
