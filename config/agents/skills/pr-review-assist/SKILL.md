# pr-review-assist

## 1. 入力収集

対象リポジトリの作業ツリー内で実行する（ブランチは問わない）。

引数 `{n}`（PR番号 or URL）があればそれを対象にする。無ければ現在ブランチの PR を対象にする。

1. `gh pr view [{n}] --json number,title,body,url,additions,deletions,changedFiles,files,commits` を実行する。
2. 取得した `url` を使い、`gh pr diff "{url}"` で差分本文を読む。

失敗した場合はエラーを確認する。認証や通信の失敗を PR 不在と決めつけず、取得できなかった情報と原因を報告する。

ファイル一覧は `files[*].path`、コミットの要約は `commits[*].oid` と `commits[*].messageHeadline` から得る。
PR 自体の差分とコミット情報を使い、head のブランチ名から `origin` の履歴を推測しない。これにより fork PR も同じ手順で扱う。
`files` の件数が `changedFiles` と一致することを確認する。
`commits` が100件なら取得上限に達した可能性があるため、`gh api graphql --paginate` で対象 PR のコミットを全ページ取得する。クエリに `$endCursor: String` 変数を宣言し、`commits(first: 100, after: $endCursor)` と `pageInfo { hasNextPage endCursor }` を含める。
ファイル、コミット、差分を追加取得できない場合は、欠けた範囲を未確認として示し、全件を確認したと扱わない。

完了条件: 対象 PR のメタデータ、ファイル一覧、コミット情報、差分本文を取得し、追加取得できなかった範囲があれば特定している。

## 2. 変更の分類

ファイルを依存層に分類する。

| 層 | 含むもの |
|---|---|
| 1. 計画 / 設計 | `docs/`, `plans/`, `*.md`, `openapi/` |
| 2. 純粋ロジック | hooks, utils, models, pure services, server actions |
| 3. 純粋ビジュアル | presentational components, `*.module.css`, stories |
| 4. 配置・状態制御 | containers, orchestrators, providers, stateful components |
| 5. 呼び出し側 | pages, route handlers, feature integrations |
| 6. 末尾の調整コミット | fix/style/refactor の小コミット、`*/generated/` や `*-schema.d.ts` などの自動生成物 |

層6はコミットの時系列ではなく性質で判定する。この PR の主目的から独立した小さな fix/style/refactor と自動生成物が層6で、時系列上の最後のコミットであっても主目的に関わるものは該当する層に入れる。

`spec/` や `*.test.*` は対象実装ファイルと同じ層に含める。複数ファイルへの同型変更は「1つ精読 + 残り{N-1}つは差分同型確認」として1件に数える。この数え方は層を小見出しに分けるかどうかの判定にだけ使う。HTML には同型変更のファイルも1ファイル1項目で全て出し、「差分同型確認」のラベルをつける。

層内が10件を超えたら機能ディレクトリ単位の小見出しに分ける。空の層は飛ばす。

層6は HTML 末尾に対象パスと注意点（生成元との対応、主目的の変更との関係）をまとめる。

続いて、主要な変更ごとに「変更前 → 変更後 → 影響する呼び出し側」を整理する。依存辺には参照・呼び出し・データ受け渡し・生成などの関係と、根拠となるパス／シンボルを記録する。差分だけで分からない関係は対象 PR の base/head のソースで確認し、未確認の関係は未確認と記す。手元の別ブランチの構造を混ぜない。

完了条件: 全変更ファイルの分類と、図に使う主要変更・依存関係・根拠・未確認範囲が確定している。

## 3. HTML を書く

`template.html`（このスキルと同じディレクトリ）を読み、配色・レイアウトを使って HTML を書く。図は Nix で配布した [mizchi/explainer](https://github.com/mizchi/explainer) の `$HOME/.agents/skills/explainer/references/figures.md` を読んで作り、生成した SVG をテンプレートに埋め込む。依存関係は `explainer` コマンドの実行環境に固定されている。初回は `explainer setup` で対応する Chromium を取得し、以後は再利用する。コマンドやスキルが未配置なら dotfiles の `just switch` で反映する。図の中間ファイルは成果物ディレクトリに置く。

### スタイルとレイアウト

テンプレートの設計図風レイアウトを保つ。上部に PR リンクと変更件数、左にページ内ナビ、本文に概要・横長の依存図・変更前後・確認点を配置する。

- 面・ノード・バッジは直角、区切りは細い罫線で揃える。角丸と影は使わない。青を接続線と見出しのアクセントにし、方眼は図の領域だけに敷く。
- 変更前後は横並びにし、責務の範囲を破線の囲みで示す。図内の番号と直下の短い解説を対応させる。関係の線に使う破線（未確認）と、責務を囲む破線はラベルで区別する。
- 狭い画面では左ナビを本文の上に移し、前後比較を縦に並べる。図は文字を縮めず枠内で横スクロールさせる。出力しないセクションの目次項目も外す。

### 図解と説明

本文は **全体像 → 主要変更の図解 → 層ごとの確認点** の順にする。図の内容と掲載基準は以下に従い、作成・検査手順は explainer の `references/figures.md` を正とする。

- **全体図を1つ必ず置く。** 変更されたモジュールと、影響を受ける呼び出し側・依存先の関係を示す。読み順の番号と依存の矢印は区別する。単一ファイルなら変更箇所の構造を図示し、独立した変更同士は接続せず並べる。
- **主要変更ごとに詳細図を置く。** 責務の移動は変更前後の比較図、処理の順序はフロー／シーケンス図、条件による振る舞いは分岐図、型や配置の変更は構造図を選ぶ。全体図が単一の変更を十分に説明する場合だけ、詳細図を兼ねてよい。
- ノードは実際のパス／シンボルと役割で表し、矢印には関係と向きを明記する。追加・変更・削除・変更なしは色と文字ラベルを併用する。未確認の関係は破線と「未確認」で区別し、図の直下に根拠パス／シンボルをプレーンテキストで添える。
- 各図に「この変更で何が変わり、どこへ影響するか」を1〜2文で添える。文章は図の読み取りとレビュー判断を補い、ソースの逐語説明は省く。PR 本文に理由がなければ「理由は PR 本文に記載なし」とする。
- §2 のパス・シンボル・関係・根拠から図ごとの `*.facts.json` を先に作る。未確認の関係は事実として記録せず、図に入れる場合は「未確認」と明示する。explainer の形式選択に従って図を作り、`explainer run figure-check.mjs <図のパス> --facts <事実シートのパス> --write`（シーン形式なら `explainer vlmkit-anim check --expect` と `layout`）で検査する。手書き SVG の事実シートには `labels` と `forbidden` を使い、`edges` の自動照合は D2 / Mermaid に使う。出力された全体・矢印のシートを図ごとに目視し、誤読する線や欠けた文字を直す。図を変更したら HTML も再生成してから表示を確認する。
- 検査済みの図をインライン SVG として埋め込む。SVG は `viewBox`、ページ内で一意な ID の `title` / `desc` と `aria-labelledby` を持たせる。複数の図を埋め込むときは ID の重複を解消する。文字を読める大きさに保ち、大きな図は分割するか図の枠内で横スクロールさせる。オフラインで表示できるよう、外部スクリプト・フォント・Mermaid の実行環境には依存しない。

前提知識を補う説明が必要なら `eli33` を必要に応じて参照する。

### 文字の収まり

- SVG の `<text>` は自動で折り返されない。長いパス・ファイル名・識別子は `/`・`_`・`-`・`.` の区切りで `<tspan>` の複数行に分け、区切りがなければ文字単位で分ける。全文を保ち、各行の `x` と `dy` を指定する。文字は16px以上、行間は1.4倍以上、ノード内の余白は `viewBox` 座標で12以上にする。
- ノード幅を先に固定せず、実際のフォントで最長行の幅と全行の高さを測り、余白を足して枠の幅・高さを決める。等幅の `.code-label` を含め、検査用 SVG にも最終 HTML と同じフォントを適用してから explainer の検査を実行する。
- 埋め込み後の HTML でも `document.fonts.ready` を待ち、各文字と所属するノード枠の `getBoundingClientRect()` を比較して上下左右が余白内に収まることを確認する。はみ出したら行分割か枠の拡張を行い、隣のノード・矢印・`viewBox` も再配置して再検査する。文字の縮小、切り取り、省略記号では解消しない。横スクロールは図全体を閲覧するために使い、ノード内のはみ出しは別に解消する。

### コードとファイル名

- ファイル名・パス・識別子・式は、見出し、説明文、確認点、図の注釈を含めて `<code>` で囲む。ファイル一覧の `.file-path` も使える。SVG では該当する `<text>` / `<tspan>` に `class="code-label"` を付ける。役割や関係の日本語説明は通常フォントのままにする。
- コード引用にはテンプレートの `.code-sample` を使い、ファイル名と言語名を添える。`<pre class="code-block"><code>…</code></pre>` 内で改行・字下げを保持し、長い行は枠内で横スクロールさせる。引用が不要な側は `.code-sample` ごと省く。
- シンタックスハイライトは生成時に付ける。対象言語に合わせ、キーワード・文字列・数値・関数名・型名・コメントを、それぞれ `token keyword` / `string` / `number` / `function` / `type` / `comment` クラスの `<span>` で囲む（例: `<span class="token keyword">const</span>`）。配色はテンプレートの明暗テーマを使う。ファイル名・単独の識別子は等幅だけでよい。言語が不明な引用は等幅の平文で表示し「言語未確認」と記す。
- `{{before_code_tokens}}` / `{{after_code_tokens}}` には、ソースの各トークンを HTML エスケープしてから表示用の `<span>` で包んだ断片を入れる。元コードのタグ・属性は常に文字として表示する。これらの断片に許可するマークアップは上記クラスの `<span>` だけで、装飾を除いた `textContent` が引用元と一致することを確認する。実行時の構文解析や CDN は不要。

### 確認点とリンク

PR への外部リンクは上部ヘッダーの PR 番号1か所に集約する。後半の図・ファイル項目・末尾ではパスをプレーンテキストで示し、ページ内の目次リンクだけを使う。差分全文は貼らず、判断に必要な引用を数行に絞る。
PR のタイトルや本文、パスを HTML に取り込む際は、テキストと属性値をエスケープする。PR 由来の値は JavaScript や SVG のマークアップとして実行せず、表示用テキストとして扱う。

- PR 全体の要約: 何をするか・なぜ必要かを前提知識なしで**3文以内**で書く。「なぜ」は PR body から取る。
- 各層に目的を1文つける。何をする層かだけを書く。
- 層1〜5の各ファイルに必ず次の3つを書く。
  1. 変更の要点。「何を」「どうした」だけの1文。
  2. 確認ポイント 1〜3個。各1行、「〜か」で終える疑問形。（呼び出し元への影響 / 境界値・エラー時 / 振る舞いが変わるか / テストの有無 のいずれかに該当するもの。思いつかない場合は「確認ポイントなし（自明な変更）」と明記して省略してよい）
  3. 精読 か 差分同型確認 のラベル
- 横断の注意点セクション（冒頭）: 振る舞いが変わるのにテストが無い箇所 / 削除された処理 / 設定・環境変数・マイグレーション / 公開シグネチャの変更。各項目1行。該当が無ければセクションごと省く。

書き方の例

| 項目 | 良い例 | 悪い例 |
|---|---|---|
| 変更の要点 | `並び替えの enum 参照を定数に集約した。` | `並び替えの選択肢を扱う enum の参照先がコンポーネント側に散っていたため、constants に集約する設計に変更した（PR本文の意図どおり）。` |
| 確認ポイント | `page.tsx からの参照漏れが無いか` | `page.tsx から移設した REVIEW_LIST_MAX_PAGE について、他の箇所からの参照が残っていて壊れていないか確認する必要があるか` |
| 層の目的 | `URL と API 条件の変換を担う層。` | `並び替え・絞り込みの型・定数、URL の searchParams と条件・API クエリ間の変換、件数/一覧取得のロジックを提供する層。` |
| 横断の注意点 | `ReviewList.spec.tsx が無いまま分岐が増えている` | `ReviewList.tsx に追加された「絞り込み中の0件は専用メッセージ、そうでなければ従来の投稿導線」という分岐と、並び替えセレクトの表示に対応する ReviewList.spec.tsx が存在しない。` |

完了条件: 全体図と主要変更ごとの図解があり、各図の関係に根拠または未確認の表示がある。最終 HTML のフォントで全ノードの文字が枠内に収まっている。全ファイルの確認点（層6は末尾の対象パスと注意点）を含み、外部リンクは冒頭1か所だけになっている。

## 4. 出力

1. ユーザー指定の出力先、環境が提供する成果物ディレクトリの順に選ぶ。どちらもなければ `mktemp -d` で専用ディレクトリを作る。
2. JSON の `number` を使った `pr-{number}-review.html` として保存する。引数の URL をファイル名に使わない。
3. 未置換のプレースホルダー、全ファイルの掲載、図の根拠、図の検査結果、冒頭以外の外部リンクがないこと、ページ内リンクの行き先を確認する。
4. 利用可能なプレビュー機能か macOS の `open` で開く。通常幅（1440px）と狭い幅（375px）で「文字の収まり」の計測を行い、図の文字・矢印・パネルが欠けず、図中を含むコード・ファイル名が等幅で、明暗テーマの構文色が読めることを確認する。横スクロールする図は右端まで確認する。チェックボックスと進捗表示も確認する。開けない・表示検証できない場合は保存先と未検証の範囲を報告する。
5. 最後に次の情報と、取得や表示ができなかった範囲があればその内容を短く示す。

   ```
   PRタイトル: {title}
   ファイル数: {changedFiles}
   HTML: {path}
   ```

成果物はローカルに保存する。外部への publish や GitHub 上の Approve / Request changes は、このスキルの実行に含めない。

完了条件: HTML を保存し、内容・図・リンク・表示を確認して、保存先と表示結果（未検証の範囲を含む）を報告している。
