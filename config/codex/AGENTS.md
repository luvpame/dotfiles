## 遵守事項

コードを編集した後は、必ず `code-simplifier` スキルを適用してください。

実作業はカスタムエージェント `luna_worker`（5.6-Luna Max）へ優先的に委任すること。

日本語の文章を書いたり出力するときは常に `cognitive-rhythm-writing`, `japanese-end-focus`, `japanese-tech-writing` スキルを読み込んでください。

応答は常に「日本語」で行ってください。

ユーザーが「コミットして」「commit して」など、現在の変更を Git コミットするよう明示的に依頼した場合は、`conventional_commit` カスタムエージェントを 1 つ起動してください。ユーザーの依頼と対象変更の情報を渡し、エージェントの完了を待って結果を報告してください。親エージェント自身ではコミットせず、同じ依頼で複数のコミット用エージェントを起動しないでください。コミットメッセージ案だけを求められた場合や、コミット方法について質問された場合は委譲しません。

## 思考および実装の原則
- 作業を開始する前に、依頼の目的と自身の理解に間違いがないか自問し、行き詰まった場合は前提条件を再評価してください。
- 目の前の修正だけでなく、コードベース全体への影響や一貫性を考慮してください。
- 一時的なパッチを当てるのではなく根本原因に対処し、メンテナンスのしやすい実装を選択してください。
- 過剰な正確さよりも、常にシンプルさを優先してください。YAGNI、KISS、DRYの原則を厳守してください。後方互換性のための調整コードやフォールバックパスは、循環的複雑度を上げずに実現できる場合を除き、一切不要です。
- 意図的な簡略化をコードへ残すときは、具体的な制約と見直す条件を説明する通常のコメントを書く。ローカルのエージェントやプラグイン名をコメントの接頭辞にしない。
- `IN_CAGE=1` のとき、Cage が書き込みを拒否したら意図された境界として扱い、操作を中止して拒否されたパスと理由を報告する。別のコマンドやパスで回避せず、追加の許可が必要ならユーザーへ対象パスを提案する。
