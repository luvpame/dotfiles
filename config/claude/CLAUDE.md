## 遵守事項
- Fable, Opus モデルを使用している場合、コードの編集は直接行わずに SubAgent を作成し、安価な Sonnet や Haiku モデルに作業を移譲すること。
- コードの編集を行った後は必ず `/code-simplifier`(小規模), `/simplify`(大規模) を Sonnet モデルを使用して簡素化を行うこと。
- 日本語の文章を書くときは常に `japanese` スキルを読み込むこと。
- ユーザーが「コミットして」「commit して」など、現在の変更を Git コミットするよう明示的に依頼した場合は、Haiku モデルのサブエージェントを作成し、 `conventional-commits` か、repo 内にコミットのスキルが用意されている場合はそのスキルを使用すること。（`commit` など）ユーザーの依頼と対象変更の情報を渡し、エージェントの完了を待って結果を報告してください。親エージェント自身ではコミットせず、同じ依頼で複数のコミット用エージェントを起動しないでください。コミットメッセージ案だけを求められた場合や、コミット方法について質問された場合は委譲しません。
- `japanese-end-focus` を読み存在する熟語だけを使用すること。

## 思考・実装の原則
- 作業前に依頼の目的と自分の理解を疑い、行き詰まったら前提から見直す
- 目先の修正だけでなく、コードベース全体への影響と一貫性を考慮する
- その場しのぎではなく根本原因に対処し、保守しやすい実装を選ぶ
- 病的なまでの正確さよりも、常にシンプルであることを優先してください。YAGNI、KISS、DRYの原則を徹底すること。後方互換性のための調整コードやフォールバックパスは、循環的複雑度を高めずに実現できる場合を除き、一切不要です。
- 意図的な簡略化をコードへ残すときは、具体的な制約と見直す条件を説明する通常のコメントを書く。ローカルのエージェントやプラグイン名をコメントの接頭辞にしない。
